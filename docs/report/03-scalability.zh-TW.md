# 3. 擴展性設計

## 預期規模

Go-Split 服務的是小團體：一趟旅行、一場烤肉、一頓聚餐。一個活動有數人到數十位
成員，以及數十到一兩百筆開銷明細。流量是突發性的：主辦人儲存後成員會查看自己的
分攤，主辦人結算時所有人會同時查看。單一活動很少每秒超過幾次儲存。

## 設計上為擴展所做的事

- **Cloud Run 上的無狀態 API。** Session 存在 PostgreSQL，任何 instance 都能處理
  任何請求。Cloud Run 在 0 到 5 個 instance 之間擴展（每個 1 vCPU、512 MiB）。
- **預覽在瀏覽器執行。** 主辦人輸入時由 WASM 引擎計算分攤，只有最後的儲存會送到
  伺服器。
- **靜態資源由 Vercel CDN 提供。** 前端頁面與 `engine.wasm` 從 CDN 載入；`/api/*`
  則原封不動轉送到 Cloud Run，不做快取，所以 API 的擴展仍由 Cloud Run 與資料庫
  決定。實測經 Vercel 轉送每個請求多約 41 ms（P50）／53 ms（P95）。
- **每個活動的寫入序列化。** 同一活動的儲存、加入與結算在交易中逐一執行。這確保
  結果正確，也限制了單一活動每秒能承受的寫入數（見下文）。
- **結算快照。** 結算後的讀取來自凍結的快照，不再重新計算。
- **PGO 流程。** 正式環境的 CPU profile 上傳到 GCS，可用於 `go build -pgo`。

## 負載測試

以 k6 進行負載測試。CI 每次以 `make load-smoke`（`GET /events`，20 RPS 持續 30 秒）
做回歸檢查。容量則以 `make load-prod` 對正式環境量測：使用真實的 session 與活動，
對五個 endpoint 送出日常讀取流量。它略過儲存與結算，因為建立這些資料需要直接存取
資料庫，而結算會永久凍結活動。

### 正式環境結果（2026-10-01）

以 `make load-prod` 直接對 asia-east1 的 Cloud Run 執行（不經 Vercel）。測試活動有
6 位成員、16 筆開銷，只有讀取；每一階段爬升 60 秒、維持 90 秒。

| RPS | P95 | 最慢的 endpoint（P95） | 錯誤／5xx | 丟棄的 iteration | 請求數 |
| --- | --- | --- | --- | --- | --- |
| 50 | 64.5 ms | `/me/details`（71.4 ms） | 0／0 | 0 | 6,375 |
| 75 | 52.9 ms | `/me/details`（58.8 ms） | 0／0 | 0 | 9,562 |
| 100 | **7.06 s** | `/events/{id}`（7.23 s） | 0／0 | 1,311 | 11,438 |

50 與 75 RPS 時都遠低於 500 ms 的目標。到 100 RPS 時沒有任何錯誤，但請求開始排隊，
P95 急遽升到約 7 秒，因此沒有繼續測 150 與 300。所有 endpoint 一起變慢，代表瓶頸是
共用資源：5 個 1 vCPU 的 instance，或約 20 條資料庫連線；測試時無法取得 GCP 指標
確認是哪一個。此外也進行過多輪測試（包括限制每個 instance 的連線數），結果沒有明顯
變化。

正式環境的讀取容量約 75 RPS，低於 300 RPS 的參考值，但仍遠高於預期規模
（單一活動很少每秒超過幾次儲存）。

## 已知限制與瓶頸

### 資料庫連線（主要限制）

- **Cloud SQL `db-f1-micro` 約允許 25 條連線**，其中幾條保留給 Cloud SQL 自己。
- **Cloud Run 上限為 5 個 instance**（`cloud_run_max_instances`），每個 instance 以
  `DB_MAX_CONNS` 限制為 4 條連線，共 20 條，剛好低於資料庫上限。CD 的 migration 步驟
  經 Cloud SQL Auth Proxy 還需要一條，餘裕很小；若提高 instance 上限或每個 instance
  的連線數，資料庫會拒絕連線。

可行做法，由便宜到昂貴：

1. 換到更大的 Cloud SQL 方案，允許更多連線。
2. 在資料庫前加上連線池代理（PgBouncer，或 Cloud SQL 託管的 pooler）。

### 其他限制

- **單一活動的寫入逐一執行。** 熱門活動在每秒 20 次儲存下維持 500 ms 以內，前提
  是連線池限制了並行數。這遠高於實際使用量，但一個很大、很活躍的活動仍會排隊。
- **分攤在讀取時計算。** 結算前，`/shares` 與 `/me/details` 每次請求都會重算所有
  明細，成本隨活動的明細數成長。實際規模下沒有問題；只有非常大的活動才值得快取。
- **冷啟動。** 縮減至零代表閒置後的第一個請求會啟動新 instance，在提供服務前先
  執行 migration 與範本 seeding。嘗試量測時，閒置 21 分鐘後仍有 instance 在執行
  （第一個請求 90 ms），所以尚未取得冷啟動數字。
- **單一 zone 的資料庫。** `availability_type = "ZONAL"`。zone 故障時資料庫會停擺
  直到恢復；已開啟備份與時間點還原。
